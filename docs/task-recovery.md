# Task recovery and paid-call ambiguity

Before a video generation call, the worker reserves a local task and writes an R2 intent at `task-recovery/<local-id>.json`. The intent records the project, external idempotency key, sanitized request settings, and a stable `taskTraceId`. After Kling returns a `generationId`, the worker adds it to the recovery record and finalizes the D1 task. A replay of the same project/key repairs D1 from that record without creating another generation. The browser keeps unresolved payload/key pairs in tab-scoped `sessionStorage` so a reload can retry with the same key; per-project drafts remain in memory only.

Kling's [MCP tool reference](https://github.com/klingai-tech/skills/blob/main/api-examples.md) documents `taskTraceId` as telemetry only: it does not reach the paid downstream service, and `query_tasks` accepts a `generationId`, not a trace ID. Therefore a process crash or lost response after the paid call but before the `generationId` is persisted cannot be resolved automatically. Such tasks become `unknown` after five minutes (or immediately after a request error). The UI labels them “状态待核对” and keeps the original client idempotency key for retry. Replaying that key returns the existing local task and never calls generation again. An administrator must compare the trace and time with Kling records before deciding whether to create a new attempt.

Polling only calls `query_tasks` for locally owned queued/generating tasks with a stored `generationId`. It never calls a generation tool. The client polls with a three-second starting interval and a thirty-second backoff ceiling, and stops after a terminal status or project switch.
